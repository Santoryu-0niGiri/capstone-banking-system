Code Review — Core Retail Ledger & Balance Mutation Engine
Reviewed against: 00_capstone-fse-spec.docx  |  Branch snapshot: capstone-banking-system.zip (post FC-23–FC-50)
1. Summary
The core banking mechanics are genuinely solid: pessimistic locking, dual-write with compensation, RFC-7807 error handling, and a real (not mocked) cross-currency saga across three services. That's the hard part, and it's done well.
But five of the eight tickets in this batch (FC-23–FC-50) have a gap between what the walkthrough claims and what the code does. Most are small, fast fixes — not redesigns. The two that matter most for a panel demo: there is no role-based access control despite the JWT already carrying roles, and the reported 9,571 TPS benchmark did not come from a real load test against the running stack.
Fix order for the days you have left: security gaps first (cheap, high-risk if a panelist tries them live), then the outbox correctness bug, then get one real JMeter run on the books before the demo.

3. Critical — fix before hardening / demo
3.1 No role-based access control, anywhere
Every service's SecurityConfig ends the same way:
.anyRequest().authenticated()
That's it — any valid JWT, customer or admin, can hit any endpoint. The role list is already being parsed out of the token into Spring authorities in JwtAuthenticationFilter, so this is a config change, not new plumbing: add .hasRole(...) rules per route.
Bigger gap in the same area: nothing checks that the caller owns the account they're debiting or crediting. Any authenticated customer can call POST /api/accounts/{id}/debit with someone else's account ID. This is worth fixing before any live demo — a panelist trying another customer's ID is a realistic thing to happen.
3.2 Every service port is exposed directly in docker-compose
Ports 8081–8086 are all published to the host. Combined with 3.1, this means the API Gateway's routing and JWT check can be skipped entirely by calling a service directly. Simplest fix for a training build: stop publishing the internal service ports, keep only the Gateway (8080) and frontend (8090) reachable from outside.
3.3 Outbox writes fail silently — breaks the atomicity guarantee
In accounts-service, AccountService.saveOutbox() wraps the outbox insert in a try/catch that only logs the error:
catch (Exception e) { log.error(...); }
The whole point of writing the outbox row in the same transaction as the balance mutation is that both succeed or both roll back together. Swallowing the exception here means a balance can change while its outbox event silently never gets written — no Kafka event, no crash, no trace. Let it propagate (or explicitly rethrow) so the enclosing @Transactional actually rolls back.
Related: outboxMasterRepository and objectMapper are wired as @Autowired(required = false), and saveOutbox() just returns if the repository is null. If that bean fails to load for any reason, every mutation silently stops producing outbox events with no error anywhere. Worth making this a hard dependency instead.
3.4 The 9,571 TPS / 0ms p95 benchmark isn't a real load test
RefactoredPathBenchmarkTest (the source of the FC-41 numbers in the walkthrough) runs entirely in-process: a no-op PlatformTransactionManager that does nothing on commit, and mocked repositories/clients standing in for Oracle, Postgres, and the Accounts REST call. It's a fine test of raw Java call overhead, but it never touches a database, the network, or Kafka — so the number doesn't demonstrate the SLA the spec is actually asking about.
The good news: a real JMeter plan already exists (tests/jmeter/debit-concurrency-baseline.jmx) and correctly targets POST /api/v1/ledger/mutate with configurable threads/ramp-up. There's no evidence yet that it's been run against the actual docker-compose stack. Run it before the demo and report those numbers instead — if they're lower than 9,571 TPS, that's expected and still fine as long as they clear 800.
3.5 Telemetry (Prometheus / Grafana / OpenTelemetry) — not started
Spec Section E calls for this explicitly and it's part of the evaluation matrix (Task 2/3 scoring). Nothing in any pom.xml or config references Micrometer, Prometheus, or OpenTelemetry. Even Spring Boot Actuator + a Micrometer Prometheus registry (a few hours of work) would cover this at training-project depth.
4. Medium priority — worth doing, not blocking
AccountMutationRequest should use @Digits(integer = 14, fraction = 4) to match TransactionRequest and the spec's precision rule, not just @DecimalMin.
transaction_master's status flip to COMMITTED (Phase 3, Oracle) is best-effort and not outbox-protected. This was a deliberate earlier design decision — Reconciliation Service catches drift here — so it's not a bug, but the Reconciliation Service itself doesn't exist in the codebase yet (only a frontend controller with mock data does). Until it's built, this drift has nothing actually watching it.
Every service's saveOutbox()-equivalent should follow the same fail-loud pattern once 3.3 is fixed — check forex-service and transaction-service for the same swallow-and-log shape.
No correlation ID threads through the saga (Transaction → ForEx → Accounts → Transaction), which will make debugging a failed cross-currency transfer harder to trace live in front of a panel.
5. Testing — what exists, what to add
Test files exist across most services (transaction-service, accounts-service, forex-service, api-gateway, login-service, registration-service), covering unit-level service logic, the cross-currency saga path, and JWT validation. That's a real foundation. For the hardening pass, prioritize:
Unit: AccountMutationRequest validation boundaries (zero, negative, > 4 decimal places) — currently untested given the @DecimalMin gap above.
Integration: run debit/credit against a real Testcontainers Oracle + Postgres, not mocks — confirms the pessimistic lock and outbox insert actually behave under real DB constraints, not just in Java logic.
Integration: force the outbox insert to fail (e.g. a bad payload) and assert the balance mutation actually rolls back — this is the test that would have caught 3.3.
Security: a 403 test per role per endpoint, once 3.1 is fixed — and one "customer A hits customer B's account" test proving the ownership check works.
E2E: the full cross-currency saga through the actual Kafka broker (not the in-process consumer test), asserting the ledger ends up with exactly two correctly-tagged legs.
Load: one real run of debit-concurrency-baseline.jmx against docker-compose, captured as the actual FC-41 evidence for the report.
